What Is This?

A Performance Engineering System, Not a Collection of CUDA Programs

KernelX is a GPU kernel performance engineering platform. Its job is to take a GPU workload, establish a reproducible performance baseline, profile its execution on real hardware, identify the limiting hardware resource, implement targeted optimized variants, and quantitatively evaluate the result.

Question 1
Why is this kernel performing the way it is?
Question 2
What change actually makes it faster?

These are the two questions every result in this project is built to answer. Not "what is the fastest number I can get?" but a measurement-grounded explanation of the hardware bottleneck and a targeted fix derived from that explanation.

Not the goal

This project is not chasing the fastest number.

Knowing that CUTLASS runs GEMM at 169 TFLOP/s is not the point. Knowing why the naive implementation runs at 5.2 TFLOP/s — and exactly which hardware constraint each step in the progression addresses — is the point. A result without an explanation is just a benchmark. An explanation grounded in a measurement is performance engineering.

The Engineering Problem

Modern AI workloads are increasingly constrained by how efficiently computation moves through GPU hardware — not simply whether the model produces the correct output. The gap between a correct naive implementation and a hardware-efficient one is not a constant factor. It is specific to the kernel, the problem size, and the hardware generation. The only way to close that gap systematically is to measure it, understand it, and act on what the measurement says.

NVIDIA's performance engineering roles explicitly involve kernels like attention, matrix multiplication, MoE routing, quantization, and data movement — using CUDA, CUTLASS, and Triton — with repeatable benchmarks, roofline analysis, regression gates, and Nsight tooling. This project is a focused implementation of that workflow on a realistic slice of those workloads, running on NVIDIA H100 hardware.

Methodology

Each workload progresses from naive through hardware-aware implementations, with Nsight Systems confirming (or refuting) the hypothesis at each step.

Every Implementation Is a Falsifiable Hypothesis

The loop only produces insight if each step makes a specific, testable claim about what the bottleneck is. When the measurement contradicts the hypothesis, that is a result — not a failure.

Hardware Analysis Concepts

Every kernel is evaluated against four hardware frameworks. These are not independent metrics — they form a consistent picture of where cycles are going.

Roofline Model

Plots kernel performance against arithmetic intensity (FLOP/byte). The H100 ridge point is 17.9 FLOP/byte — below it the kernel is memory-bound; above it, compute-bound. Every optimization in this project moves a kernel along or toward the relevant ceiling.

Speed-of-Light

What percentage of peak hardware throughput is the kernel achieving? Compute SOL %, HBM SOL %, L1/L2 SOL %. A kernel at 13% compute SOL and 5% HBM SOL is compute-bound with significant headroom — the right tool is Tensor Cores, not memory optimization.

Occupancy — Not a Direct Metric

Occupancy (% of max warps active) is a common trap. Higher occupancy does not mean higher performance. What matters is whether there are enough in-flight warps to hide memory latency. A compute-bound kernel at 50% occupancy can outperform a memory-bound kernel at 100%. Occupancy is a tool for diagnosing latency hiding, not an objective.

Warp Stall Analysis

When a warp cannot issue an instruction it stalls. The dominant stall type identifies the bottleneck class: long_scoreboard stalls indicate HBM latency (memory-bound); math_pipe_throttle indicates the compute pipe is saturated (compute-bound); mio_throttle indicates memory instruction queue pressure. Not every stall is a performance problem — a stall that is fully hidden by other warps costs nothing.

Workload 1

GEMM — Matrix Multiplication

General matrix multiplication (C = A × B, M=N=K, fp32) is the most compute-intensive primitive in deep learning. Five implementations form a deliberate progression from naive global-memory (5.2 TFLOP/s) through manual WMMA Tensor Core access (27.9 TFLOP/s) to CUTLASS TF32 (169.3 TFLOP/s) — a 32.6× wall-clock improvement, each step exposing a specific hardware constraint on the H100.

naive

O(2N) global loads per output element. Every thread reads full rows and columns independently with no data reuse. L2 miss-dominated — most cycles stall waiting on HBM.

Roofline: memory-bound — AI ≈ 1 FLOP/byte vs H100 ridge 17.9 FLOP/byte. Bottleneck is global memory, not compute.

tiled

Shared memory tiling with 32×32 blocks. Global traffic drops to O(2N/tile) — threads in the same block cooperatively load a tile once and reuse it 32 times. 1.7× speedup.

Roofline: still memory-bound — AI improves to ≈ tile/2 FLOP/byte but register pressure limits tile size to 32.

tuned

Register-blocked accumulator (8×8 per thread), float4 vectorized loads, fully unrolled inner loop. 4.1× speedup.

Roofline: compute-bound — AI crosses the ridge point. FP32 FMA utilisation ≈ 35–40% of peak. Memory is no longer the ceiling.

WMMA

Manual Tensor Core access via nvcuda::wmma. FP16 inputs, FP32 accumulator. Each warp owns 2×2 fragments (32×32 output), dispatched with mma_sync. 27.9 TFLOP/s — 5.4× over naive, but 6.1× behind CUTLASS.

Roofline: aimed at the Tensor Core ceiling but not reaching it — without cp.async double-buffering, long-scoreboard stalls from synchronous global→shared loads dominate. The 6.1× gap to CUTLASS is precisely the cost of missing software pipelining.

CUTLASS

TF32 Tensor Cores via mma.sync, multi-stage software pipeline (cp.async + ldmatrix) overlaps memory and compute. 32.6×.

Roofline: operating against the Tensor Core ceiling — a fundamentally different (and higher) compute roof than FP32 scalar. Near H100 FP32 peak at 169 TFLOP/s.

Triton

Autotuner selects tile dimensions, block sizes, and pipeline depth at compile time. 139 TFLOP/s at N=4096 — 82% of CUTLASS.

Takeaway: Triton closes the gap from abstraction to hand-tuned CUDA at large N, confirming the autotuner finds near-optimal tiling without manual register analysis.

Triton: High-Level GPU Programming vs Hand-Tuned CUDA

Triton (OpenAI) is a Python DSL that compiles to PTX without requiring the programmer to manage registers, shared memory layout, or instruction scheduling explicitly. The autotuner exhaustively searches tile dimensions and block sizes at compile time, selecting the configuration that maximizes throughput on the target GPU.

What Triton abstracts away

Register blocking, shared memory bank conflicts, vectorized load alignment, loop unrolling, pipeline depth. The programmer writes the tile logic; the compiler handles the rest.

What you give up

Direct mma.sync Tensor Core access, fine-grained cp.async pipeline control, and PTX-level instruction selection. CUTLASS's 18% lead at N=4096 comes entirely from these.

What 82% of CUTLASS at N=4096 Means

At small N (512), CUTLASS is 1.8× faster than Triton — the autotuner hasn't found optimal tile dims for small problem sizes and the per-launch overhead matters more. At N=4096 the gap closes to 18%. This is the autotuner's correct regime: it finds near-optimal tiling for large, latency-insensitive problems without manual register analysis.

The practical conclusion: Triton is the right tool when you need a custom kernel fast and the problem is large enough to amortize autotuner search cost. CUTLASS is the right tool when you need every last TFLOP/s and can afford to manage pipeline stages manually. This project implements both so the tradeoff is measured, not assumed.

Workload 2

Softmax

Softmax over rows of a [4096, 4096] matrix. The naive implementation provisions 1024 threads per row but all threads block waiting on a global max broadcast — synchronization cost dominates the actual arithmetic.

Softmax kernel time — naive vs online (N=4096, ms, lower is better)

300× Faster

The online warp kernel (Milakov & Gimelshein 2018) assigns one warp per row, computes (m, d) simultaneously using warp butterfly __shfl_down_sync, and completes in a single pass with no __syncthreads. The naive kernel's bottleneck is not arithmetic — it is the global synchronization point that serializes all 1024 threads into a broadcast that could be done by a single warp.

Workload 3

LayerNorm

Layer normalization over a [4096, 4096] matrix (normalize each row). The naive implementation requires three separate HBM passes; the Welford online algorithm collapses them.

LayerNorm kernel time — naive vs Welford (N=4096, ms, lower is better)

180× Faster — Why?

The naive kernel reads X twice (once for mean, once for variance) then writes Y — three HBM passes. Welford's online algorithm computes mean and M₂ simultaneously in a single forward sweep — two HBM passes total. At this problem size the dominant cost is not arithmetic but over-provisioning: a 1024-thread block processes 4096 elements while most threads idle in the reduction phase. The Welford kernel assigns one warp per row and completes the same work with 32 active threads instead of 1024.

Workload 4

Attention — FlashAttention

Self-attention (Q, K, V ∈ R^{N×64}, fp32/fp16, head_dim=64). The naive O(N²) algorithm materializes the full N×N attention matrix in HBM. FlashAttention rewrites the computation in tiles to avoid HBM materialization entirely.

Attention throughput by sequence length (TFLOP/s)
Implementation N=2048 Kernel N=4096 Kernel Speedup vs Naive (N=4096)
cuda_naive1.100 ms4.327 ms1×
cuda_flash0.253 ms0.507 ms8.5×
cuda_flash_fp160.247 ms0.492 ms8.8×

The Most Important Result: FP16 Is Slower Despite Halved Memory Traffic

This is the central engineering finding of this project. The hypothesis was: FP16 halves HBM traffic, so it should be faster. The measurement said no.

What Nsight Systems showed: FP16 H2D footprint is exactly half (1.6 MB vs 3.1 MB at N=4096) — confirming the memory traffic really is halved. But kernel time barely changed: 0.492 ms vs 0.507 ms FP32. The bandwidth saving is real. It just doesn't matter.

Why: At peak 7.8 TFLOP/s, cuda_flash operates at 13% of H100's FP32 ceiling of 60 TFLOP/s. The kernel is compute-bound — it is waiting on the ALU, not on HBM. The memory roofline at 3.35 TB/s is not the active constraint. Halving traffic toward a ceiling you're not hitting changes nothing.

What would actually work: Tensor Cores (WMMA). wmma::load_matrix_sync with 16×16×16 FP16 fragments shifts the compute ceiling from 60 TFLOP/s to ~312 TFLOP/s — a potential 40× over current throughput. FP16 only wins once you're using the right execution unit for it.

Why FlashAttention Is 8.5× Faster Than Naive

cuda_naive materializes the full N×N attention matrix in HBM. At N=4096, that's 256 MB of intermediate scratch written and read back — 4·N²·4 bytes for one attention head. Memory traffic scales as O(N²). FlashAttention tiles Q, K, V in SRAM and runs the online softmax across tiles without ever writing the N×N matrix. HBM traffic drops to O(N·D). The 8.5× speedup is not from a faster algorithm — it is from eliminating the dominant memory traffic entirely.

Workload 5

Reduction

Parallel sum reduction across arrays of size N. Demonstrates the latency-vs-bandwidth regime transition that governs whether a synchronization optimization is visible in wall-clock time.

Reduction kernel time vs N (ms, lower is better)

Latency vs Bandwidth Regimes

Warp-shuffle elimination of __syncthreads barriers helps at small N, where the kernel is in the latency regime — synchronization overhead is a meaningful fraction of total time. At large N both implementations converge because the kernel becomes HBM-bandwidth-bound: arithmetic intensity ≈ 0.25 FLOP/byte, well below the ridge point. No amount of intra-block optimization changes the dominant cost once the kernel is waiting on memory bandwidth.

Workload 6

Data Movement — PCIe Transfer

Host-to-device transfer benchmarks quantifying the cost of different allocation strategies at 256 MB. Understanding PCIe behavior is a prerequisite for accurate end-to-end profiling.

H2D bandwidth by transfer type (GB/s, 256 MB)

Why Pinned Memory Is ~5.6× Faster Than Pageable

Pageable transfers require CUDA to stage data through an internal pinned bounce buffer before the DMA engine can initiate — adding a CPU memcpy to the critical path. cudaMallocHost allocates page-locked memory that the DMA engine reads directly at near-PCIe ceiling. Bidirectional throughput exceeds the unidirectional peak because PCIe is full-duplex: upstream (H2D) and downstream (D2H) lanes operate independently with separate DMA engines, summing to 86.8 GB/s combined.

GEMM — Algorithmic Improvements Scale Differently

GEMM is measured on both platforms at N=1024 (the largest size available on T4). The key observation: hand-written CUDA kernels (naive → tuned) produce similar absolute speedups (~6× on both platforms), but Triton and CUTLASS show a 10× H100 advantage because they target Tensor Cores — TF32 on H100 vs SIMT-FP32 on T4.

Why the Speedup Gap Widens at N=4096

At N=4096 (H100 only), CUTLASS reaches 169 TFLOP/s — a 32.6× speedup over cuda_naive. On T4, the same code progression peaks at ~12× at N=1024 because T4 uses CUTLASS's FP32 SIMT path (no TF32 Tensor Cores). The H100 TF32 path operates on a fundamentally higher compute ceiling: 989 vs 60 TFLOP/s. The implication: writing a good tiled CUDA kernel captures most of T4's compute budget; the same kernel on H100 leaves ~93% of peak untouched.

This is why production training frameworks (PyTorch, JAX) use cuBLAS/CUTLASS rather than hand-written GEMM even when the hand-written kernel "looks fast" — the gap only manifests at Ampere/Hopper scale, and only if the kernel is Tensor-Core-aware.

FlashAttention — Bandwidth Determines the Benefit

FlashAttention rewrites the attention computation to avoid materializing the N×N attention matrix in HBM — replacing O(N²) HBM reads/writes with O(N) on-chip SRAM passes. How much that matters depends entirely on HBM bandwidth.

FlashAttention Is More Impactful on T4 Than H100

FlashAttention delivers a 7.9× speedup on T4 but only 4.1× on H100 — the lower-bandwidth GPU benefits more from the algorithm that eliminates HBM traffic. On T4 (320 GB/s), the O(N²) matrix materialize in the naive kernel saturates memory bandwidth; FlashAttention's O(N) HBM traffic frees the bottleneck. On H100 (3,350 GB/s), the naive kernel is less bottlenecked, so the same algorithmic savings produce a smaller relative gain.

The practical implication: FlashAttention matters on every GPU but provides the largest absolute wall-clock savings on memory-bandwidth-limited hardware. As sequence lengths grow, the O(N²) penalty re-appears even on H100 — which is why FlashAttention is standard regardless of GPU generation.

Summary: What Changes Between GPU Generations

Compute-bound workloads

GEMM with CUTLASS/Triton: ~10× improvement. Tensor Core throughput scales 15×, but the gap is partially offset by occupancy and pipeline differences.

Memory-bound workloads

Softmax, LayerNorm, Reduction: ~10× improvement proportional to HBM bandwidth ratio (3350 / 320 GB/s ≈ 10.5×). Algorithm improvements scale the same on both.

Algorithm-sensitive workloads

FlashAttention: larger relative gain on T4 because the HBM bottleneck is more severe. The right algorithm matters more when the hardware has less bandwidth headroom.

Engineering Infrastructure

Benchmarking & Profiling Pipeline

Results are only as trustworthy as the measurement infrastructure. KernelX treats the benchmark runner and profiling pipeline as first-class engineering artifacts.

Benchmark Runner

CUDA event timing with configurable warmup and iteration counts. Reports median, P95, and TFLOP/s. All results written to canonical JSONL records tagged with git commit hash, GPU model, and timestamp.

Nsight Systems Pipeline

profile_nsys.sh sweeps all workloads. parse_nsys.py extracts kernel timing from --stats=true tables into nsys_records.jsonl, integrated into analyze.py.

Regression Detection

compare.py flags when a code change degrades performance vs the canonical record — prevents inadvertent regressions from surviving a commit.

SLURM Integration

Real HPC cluster (MSOE ROSIE), H100 dgxh100 partition. Automated build + profile in a single job submission. Results pull back via SLURM output files.

Nsight Systems vs Nsight Compute — Why nsys, Not ncu

The original design called for Nsight Compute (ncu) to capture hardware Speed-of-Light metrics: compute %, HBM %, arithmetic intensity, occupancy, and warp stall breakdown. On ROSIE's H100 nodes, ncu is blocked.

ToolMechanismWhat it capturesROSIE status
ncu Hardware perf counters via CAP_PERFMON Compute SOL %, HBM SOL %, arithmetic intensity, occupancy, per-warp stall type Blocked — perf_event_paranoid=4 locks hardware counters system-wide. Requires sysadmin to set ≤ 2.
nsys CUDA driver API callbacks (no hardware counters) Kernel wall-clock timing (avg/med/min/max), instance count, CUDA API overhead, H2D/D2H transfer bandwidth Working — driver callbacks are unaffected by perf_event_paranoid.

The Engineering Response

Rather than stopping at the permission error, the profiling pipeline was redesigned around nsys. A custom parser (parse_nsys.py) was written to extract structured data from nsys --stats=true fixed-width table output — a format with no existing parser. The result is kernel timing stable to ±1% across 10 launches, confirmed PCIe bandwidth measurements, and CUDA API overhead per workload.

The hardware SOL / arithmetic intensity data that ncu would have provided is instead derived from first principles: arithmetic intensity is calculated from the known FLOP count and measured memory traffic, and roofline position is determined analytically against published H100 specs (60 TFLOP/s FP32, 3.35 TB/s HBM3, ridge point 17.9 FLOP/byte). Every roofline claim in this report is grounded in that calculation, not in a tool readout.
